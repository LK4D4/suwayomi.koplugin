# WebUI Parity Matrix

This matrix is a planning reference for Suwayomi WebUI and server capabilities that might improve the KOReader plugin. It helps keep parity work deliberate: prioritize capabilities that improve e-ink browsing, library organization, local CBZ downloads, and read-state workflows, and avoid copying WebUI behavior that KOReader already owns.

Before implementing any row, re-check the relevant Suwayomi WebUI/server documentation and the current server GraphQL schema for the target supported server version. API feasibility below is evidence for prioritization, not an implementation guarantee.

Sources reviewed on 2026-05-29:

- `docs/superpowers/specs/2026-05-22-plugin-roadmap.md`

| WebUI or Server capability | Current plugin support | KOReader value | API feasibility | Device risk | Recommended priority | Notes or evidence |
| --- | --- | --- | --- | --- | --- | --- |
| Persistent source preferences | Missing; plugin supports per-search source filters and persists source filter drafts separately. | High: many sources need source-specific settings before search/browse is useful. | Unknown; current query builders fetch source filter schemas, not persistent source preference schemas. Requires current schema validation. | Medium: dynamic forms can be inconsistent and hard to present on e-ink. | High | README lists source preferences as a current limit; keep distinct from search filters in `suwayomi/source_filters.lua`. |
| Extension repositories | Missing repository management; plugin can fetch extensions and install/update/uninstall them. | High: custom repos may be required for source setup. | Unknown; extension records expose repo metadata, but current plugin queries only fetch and mutate extensions. Requires schema validation for repository CRUD. | Medium-high: repository changes affect all sources and need confirmation. | High | README lists extension repository management as a current limit; `suwayomi/api/queries.lua` includes extension fields and mutations, not repository mutations. |
| Completed download history | Missing; Downloads focuses on active, queued, and failed local CBZ downloads. | High: improves cleanup, retry confidence, and offline storage visibility. | Locally feasible from queue/download records first; broad filesystem scans are possible later but should stay under plugin-managed paths. | Medium: filesystem scans can be slow and cleanup can be destructive if path bounds are wrong. | High | README lists completed download history as a current limit; architecture defines device-local queue and source-scoped paths. |
| Save source searches | Missing as a reusable saved-search list; last source filter/search draft is persisted per source. | Medium-high: useful for repeated e-ink browsing with fewer taps. | Locally feasible in plugin settings; no server mutation required for first slice. | Low-medium: must avoid stale source/filter draft interactions. | High | WebUI README lists saved source searches; roadmap suggests this as the first Browse Triage slice. |
| Hide in-library manga while browsing | Supported: Browse settings include `Hide in-library results`, and source results are filtered when `manga.in_library` is true. | Medium-high: reduces noisy source results on slow screens. | Already feasible through existing source manga fields and local browse setting. | Low: filtering is local, but depends on server-provided `inLibrary` accuracy. | Done / maintain | WebUI README lists the capability; current code implements `hide_in_library_results` in settings and source result filtering. |
| Duplicate warning when adding manga | Missing dedicated warning; rows can show in-library state and add action is hidden when the exact result is already in library. | Medium-high: prevents library clutter. | Partly feasible with existing `inLibrary`; stronger duplicate detection needs library matching or server support and should be schema/performance checked. | Medium: eager duplicate checks could be slow and false positives are disruptive. | High | WebUI README lists duplication checks; current plugin supports library add/remove mutations but not a confirmation/warning flow. |
| Category change management | Read-only library category browsing is supported; changing manga categories is missing. | Medium: useful for library organization from device. | Unknown; current plugin queries categories and manga category memberships, but has no category update mutation. Requires schema validation. | Medium: picker UX and multi-category state need clear confirmation. | Medium | Architecture documents category browsing; roadmap suggests a single-manga category picker as first slice. |
| Chapter bookmarks | Missing; plugin supports read/unread changes and local download state, not bookmark state. | Medium: common chapter triage state. | Unknown but likely server-backed because WebUI supports chapter bookmark actions; requires schema validation for chapter fields/mutations. | Low-medium: bookmark markers must stay visually distinct from read/download markers. | Medium | WebUI README lists chapter bookmark actions; current plugin chapter queries only request `isRead`, not bookmark fields. |
| Library latest updates | Missing dedicated latest-updates view. | Medium: helpful for picking new chapters, but can be noisy on e-ink. | Likely server-backed: Server README lists latest updated chapters; exact GraphQL query and pagination require schema validation. | Medium: potentially heavy list with frequent refresh and sorting. | Medium | Server README lists viewing latest updated chapters; not present in current plugin query builders. |
| Tracking integrations | Missing. | Medium for some users; low for users who only need local KOReader read-state sync. | Server supports tracking providers, but setup/update APIs and auth flows require schema and UX discovery. | High: provider auth, account state, and sync conflicts are broad scope. | Later | Server README lists tracking; keep separate from existing read/unread sync ledger. |
| Manga migration | Missing. | Medium for occasional source changes, but uncommon and risky on an e-ink device. | Server/WebUI capability exists, but API workflow requires schema validation and careful UX design. | High: wrong migration can alter library organization and reading continuity. | Later | WebUI README lists source migration; roadmap classifies migration as later work. |
| Server-side download queue | Missing by design; plugin uses KOReader-device-local CBZ downloads. | Low-medium: may help users who also manage server downloads, but conflicts with the local CBZ model. | Server capability exists, but integrating it would be a separate workflow from local downloads. | High: hidden server-side side effects would violate plugin principles. | Later / explicit request | README states the plugin does not use or manage Suwayomi's server-side download queue. |
| WebUI reader modes/settings | Not applicable; downloaded chapters open in KOReader's normal reader. | Low: KOReader owns reading modes, scaling, themes, keybindings, and page behavior. | Not needed for this plugin. | High: duplicating reader behavior would create conflicting controls and maintenance cost. | No | Product principles say not to rebuild WebUI reader modes; README says the plugin is not a custom manga reader. |
